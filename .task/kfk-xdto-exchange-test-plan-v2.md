# кфкОбменДаннымиXDTOСервер: план и чек-лист тестирования v2

Дата: 11.09.2026. Статус: новый план; тесты, XDTO-пакеты и исходники 1С в этой работе не изменены.

Основа — [план v1](kfk-xdto-exchange-test-plan.md). Сведения v1 о методах, пакетах, фикстурах и подозрительных местах служат исходной картой; их актуальность перед реализацией проверяется через назначенные инструменты. V2 не является отчётом об уже достигнутом покрытии.

## 1. Цель и границы

Защитить от искажения значений, неверной идентификации, перезаписи чужих данных, дублирования объектов и ложного успеха при ошибке конвертации или записи. Проверки должны оставаться понятными и локальными при изменении контракта.

V2 заменяет цель «все применимые комбинации, каждый метод и 100% строк» на полное покрытие выбранных критичных контрактов и риск-ориентированное покрытие остальной логики. Это осознанное изменение критериев относительно v1, а не заявление о сохранении 100% всех сценариев. Реестр 171 метода v1 остаётся картой навигации, не списком обязательных отдельных тестов.

- [ ] Для каждого риска потери/искажения данных проверить нормальный исход, опасный отказ и значимые границы.
- [ ] Все достижимые исходы решений об идентификации, сохранении/очистке значения, записи, отказе и транзакционном результате связать с тестами. Существенные взаимодействия условий обязательны.
- [ ] Сохранить самостоятельные проверки EnterpriseData и CUSTOM там, где формат меняет результат или маршрут.
- [ ] Общую форматонезависимую логику подробно проверить один раз; принадлежность к двум форматам не является основанием дублировать тест.
- [ ] Пробелы в строках/ветвях разбирать по риску. Общий процент не компенсирует непроверенную критичную запись или идентификацию.

## 2. Паттерны из других языков

| Паттерн | Применение | Защита от избыточной сложности |
|---|---|---|
| Arrange–Act–Assert | Минимальная подготовка → одно преобразование/обновление → один наблюдаемый контракт | Связанные поля проверяются вместе; ошибки разных этапов не сливаются в один тест |
| Table-driven tests / pytest | Компактная таблица входа и независимого ожидания для скалярных значений, обязательности или выбора правила | Каждая строка имеет имя и считается запуском; не перемножать формат × тип × направление × ошибку |
| Test Data Builder | Минимальные валидные компоненты, правило, исходный объект; тест явно меняет только значимый признак | Конструктор не прячет второй объект, вызов конвертера или вычисление ожидаемого результата |
| Sociable unit tests | Настоящие внутренние преобразования и помощники в одном тесте контракта | Реальный XDTO и ИБ проверяются на подходящем компонентном уровне |
| Golden master / approval testing | Небольшие независимые эталоны сообщения для ED и CUSTOM, проверенные человеком | Не сохранять слепок всего объекта платформы; не принимать автоматически новый эталон после падения |
| Property/metamorphic testing | Повторный импорт сохраняет идентичность; перестановка независимых свойств не меняет результат; чужое поле не портится | Предусловия свойства указаны явно, порядок ТЧ и значимые типы не нормализуются |
| Model-based/stateful testing | Последовательность создать → обновить → повторить → ошибочный импорт с проверкой состояния после каждого шага | Несколько коротких фиксированных последовательностей вместо универсального генератора конвертации |
| State-based assertions / gMock | Проверять сообщение и ИБ, а не все внутренние вызовы | Вызовы проверять только на внешней границе обработчика, где аргументы/кратность/порядок — контракт |
| Mutation testing как критерий силы | Тест должен обнаружить запись при отказе, поиск по префиксу, потерю нуля, выбор чужой ссылки | Без инструмента это проверка дизайна, а не измеренный mutation score |

Источники: [pytest: параметризация](https://docs.pytest.org/en/stable/how-to/parametrize.html), [Martin Fowler: Unit Test](https://martinfowler.com/bliki/UnitTest.html), [GoogleTest: gMock Cookbook](https://google.github.io/googletest/gmock_cook_book.html), [Hypothesis: stateful tests](https://hypothesis.readthedocs.io/en/latest/stateful.html), [PIT: mutation testing](https://pitest.org/). Конкретные инварианты и матрицы ниже разработаны для этого модуля. Наличие аналогичной библиотеки генеративных тестов в YAxUnit не предполагается.

## 3. Ограничение объёма

Предварительный ориентир — 140–220 именованных запусков основного регрессионного набора, включая параметры, ED/CUSTOM и компонентные проверки. Это оценка для пилота, не обещание достаточности и не жёсткий предел. Превышение 220 требует ревью повторений и обоснования новых контрактов; необходимые критичные случаи сохраняются.

- [ ] Считать процедуры, параметризованные запуски и примеры генерации раздельно. Цикл на тысячи входов не считается сокращением набора.
- [ ] Отдельно измерять подготовку фабрики/правил, создание данных, конвертацию и очистку.
- [ ] Общие быстрые проверки отделить от компонентных с настоящим XDTO и ИБ; последние относятся к категории `Интеграционные`.
- [ ] При более чем 8 строках одной параметризации проверить уникальность обнаруживаемых ошибок; это сигнал ревью, не запрет на полную небольшую критичную таблицу решений.
- [ ] Один тест проверяет один наблюдаемый контракт. Допустимы несколько полей одного результата, недопустимы несвязанные маршруты за общим тестовым именем.
- [ ] Не создавать отдельные тесты для всех констант, геттеров и конструкторов, если их нарушение обнаруживает тест использующего их контракта. Самостоятельные публичные соответствия/схемы структуры проверять компактно.

## 4. Матрица применимости форматов

Вместо полного произведения измерений каждый механизм получает владельца подробной проверки и минимальное подтверждение подключения к публичному маршруту.

| Механизм | Подробная проверка | Подтверждение маршрута |
|---|---|---|
| Независимый от схемы разбор инструкции, вложенный путь, состояние протокола | `Общее`, один раз | Применимые маршруты ED/CUSTOM используют настоящий помощник |
| Примитивы и ограничения тестового формата | CUSTOM на реальном TestConversion | Экспорт и импорт независимых эталонов |
| Общие свойства, ключевые структуры, Ref, составные значения, AdditionalInfo | ED на настоящем EnterpriseData_1_8_6 | Экспорт и импорт реальных типов ED |
| Null/пустые значения, UUID, идентификация и обновление | Общее ядро + отдельные случаи на границе формата | ED и CUSTOM для отличающегося извлечения/представления |
| Транзакции, ошибка записи и сохранность чужих данных | Одна полная матрица на минимальной доступной фикстуре, если путь одинаков | В другом формате — нормальная запись и критичный отказ через его реальный маршрут |
| Расширения namespace и производные типы | Реальные типы нужных пакетов | Только применимые форматы; нельзя имитировать ED сменой URI |
| Специфические типы объектов ИБ | По уникальному поведению типа: документ, справочник, регистр и т. п. | Не размножать на все схемы без различия алгоритма |

- [ ] Для каждого XC-контракта ниже указать `Общее`, `ED`, `CUSTOM` или конкретные варианты обоих форматов.
- [ ] Обосновать общность пути по актуальной реализации; при отличии алгоритма разделить тесты.
- [ ] Выбрать реальные типы и готовые правила ED. Для CUSTOM сверить импортированный пакет с YAML из v1. Отсутствующая фикстура — открытая зависимость, не успешная проверка.
- [ ] Статус каждого применимого механизма отдельно виден для ED/CUSTOM: проверен, закрыт общей проверкой с обоснованием, неприменим с причиной, не проверен.
- [ ] Формы TestConversion и W01–W16 из v1 использовать как каталог возможностей, не как указание перемножить их. Для каждого W-пункта оставить решение: нужен выбранному контракту, уже обеспечен или отложен с риском.

### Публичные маршруты

- [ ] XC-E01 ED: экспорт минимального реального объекта с ключевыми свойствами и вложенной ссылкой → независимо заданное сообщение.
- [ ] XC-E02 ED: импорт независимого сообщения → правильный объект и ссылка; повторный импорт не создаёт дубликат.
- [ ] XC-E03 CUSTOM: экспорт готового справочника с двумя различимыми строками ТЧ → независимый эталон.
- [ ] XC-E04 CUSTOM: импорт независимого сообщения → создание, затем обновление того же UUID без потери чужих полей.
- [ ] XC-E05 Регистры: отдельный маршрут для каждого реально различающегося поддерживаемого механизма записи; готовые TestRegister/TestRegisterRs/TestAccumulationRegister из v1 проверить на применимость. Наличие правила не доказывает поддержку импорта.
- [ ] XC-E06 ED и CUSTOM: критичный отказ через публичный маршрут не маскируется успехом; следующий корректный вызов со свежим контекстом независим. Полную матрицу всех ошибок повторять на обоих форматах только при различии обработки.

Эти маршруты подтверждают соединение частей, а не повторяют каждую локальную границу. Связанные шаги «создать → обновить → повторить» допустимы в одном stateful-тесте идемпотентности с проверкой после каждого шага; отдельные тесты не зависят друг от друга.

## 6. Как сокращать матрицы без потери чувствительности

### Пустые значения

Не строить произведение всех типов × всех схем × всех объектов ИБ × всех настроек. Сначала явно определить семантические классы: отсутствие свойства, Null, Неопределено, типизированное пустое значение и заполненное значение. Для каждого класса выбрать применимую настройку, которая меняет решение. Число 0, Ложь и пустая строка не считаются автоматически эквивалентными: у них разные преобразования типов.

- [ ] Для XC06 вести компактную таблицу `операция → присутствие поля → значение/тип → политика → ожидаемое значение/сохранение → форматный вариант`.
- [ ] Проверять обновление заранее заполненного объекта: загрузка нового пустого объекта может не обнаружить пропущенное присваивание.
- [ ] Ожидания Null, отсутствующего поля и пустой ТЧ согласовать с контрактом; при неясности оставить открытый пункт, не брать текущее поведение за норму.

### Идентификация и запись

- [ ] Использовать базовый успешный случай и отдельные строки для каждого решения о выборе ссылки, fallback, запрете создания и записи.
- [ ] Сохранить опасные сочетания: отсутствующий UUID + совпадение по полям; конкурирующие приоритеты; существующий объект + непереданное переименованное поле; ошибка после частичного изменения.
- [ ] Для небольших критичных таблиц, например транзакция включена/выключена × успех/ошибка, оставить полный перебор. Попарный отбор не доказывает атомарность или правильность приоритетов.

### Свойства и эталоны

- [ ] К независимым эталонам экспорта/импорта добавить ограниченный round-trip только для обратимых преобразований. Две симметричные ошибки могут компенсироваться, поэтому round-trip не заменяет эталоны.
- [ ] При сравнении JSON нормализовать только незначимый порядок полей объекта. Не скрывать типы, отсутствие поля, Null, порядок массива, точность чисел или дат.
- [ ] Для метаморфных проверок заранее указать предусловия: перестановка только независимых свойств, сохранение семантики правил и отсутствие обработчика, зависящего от порядка.
- [ ] Начать с небольшого фиксированного корпуса. Если позже используется генерация, задать бюджет примеров, воспроизводимый seed и сохранять минимальный найденный контрпример; отдельно считать примеры и время. Не строить собственный аналог Hypothesis в рамках этого плана.

## 7. Фикстуры и границы изоляции

- [ ] Проверить текущую ревизию, точки входа и готовые фикстуры через разрешённые MCP: `kfk-unit` для тестов, разрешённые индексы зависимостей для анализа, `unit-edt:8768` для live-состояния/диагностики/изменений.
- [ ] До авторинга выбрать владельца `unit`, серверный контекст, имена по правилам YAxUnit и размещение тестов/помощников. Декларативная регистрация не создаёт данные и не вызывает продукт.
- [ ] Использовать публичные конструкторы `ЮТест.Данные()` и предметно корректные значения. Минимальная фикстура валидна без скрытых «исправлений» в Act.
- [ ] Переиспользовать неизменяемые схемы/ресурсные файлы; изменяемые компоненты, правила, стек и объекты создавать заново. Общий контекст не хранит результат предыдущего теста.
- [ ] Реальные XDTO-типы не заменять структурами в тестах фабрики, наследования, ограничений и сериализации. Мокировать только внешних обработчиков, когда проверяется граница их вызова.
- [ ] БД проверять специализированными утверждениями `ЮТест.ОжидаетЧтоТаблицаБазы(...)`; проверять не только созданное, но и неизменность контрольных объектов/строк.
- [ ] Для обычной записи выбрать подходящую изоляцию. Проверки собственных commit/rollback, проведения и нескольких зависимых записей не помещать в обёртку, скрывающую проверяемый эффект; нужен отдельный тестовый контур и явное восстановление.
- [ ] Учитывать, что удаление данных, созданных тестовым API, не откатывает изменение существующих записей. Очистка выполняется также после ожидаемой ошибки.
- [ ] Ошибка разрешения XDTO-зависимости и пропуск теста не считаются покрытием. Недостающие ED-типы/фикстуры фиксируются по конкретному XC-ID.
- [ ] Не изменять base, examples, adapter, YAML в tools или ядро YAxUnit в рамках unit-задачи. Необходимые зависимости и изменения продукта оформить отдельным scope.

## 9. Порядок внедрения и приёмка

- [ ] Этап 1: матрица применимости, ожидания неоднозначных случаев, реальные ED/CUSTOM-фикстуры, пилот пустых значений/идентификации/эталонов.
- [ ] Этап 2: оставшиеся P0, запись/транзакции/ТЧ, критичные дефекты и реальные публичные маршруты.
- [ ] Этап 3: P1, редкие типы по подтверждённому риску, очистка дублирующей подготовки и доказанных повторов.
- [ ] На изменении запускать затронутые контракты и быстрые P0. Перед слиянием — весь основной регрессионный набор с обоими форматами. Перед выпуском — все применимые реальные маршруты и проверки транзакционных эффектов.
- [ ] Для полной приёмки все применимые обязательные P0/P1 и публичные маршруты завершены успешно; исключения и отложенные риски не выдаются за выполненный план.
- [ ] Для XC01–XC24 и XC-E01–XC-E06 заполнены вход, формат, ожидаемый результат, тест, уровень, статус и ревизия. У каждого P0 есть содержательные утверждения результата и побочных эффектов.
- [ ] Все критичные решения и известные опасные сочетания проверены; пробелы измеренного покрытия разобраны по риску. Недостижимые строки документированы без искусственного исполнения.
- [ ] Нет неперенесённого уникального критичного сценария v1; каждому W/R-пункту назначена судьба. Неисправленный P0 или недоступная обязательная фикстура препятствуют полной приёмке.

- [ ] Зафиксированы процедуры, запуски, примеры генерации, время и сложность фикстур до/после. Порог количества служит ревью стоимости, а не основанием удалить защиту данных.
