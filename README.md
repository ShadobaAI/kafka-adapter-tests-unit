# 1С: Адаптер Kafka — Unit-Тесты

![Платформа](https://img.shields.io/badge/1С-8.3.21+-blue)
![EDT](https://img.shields.io/badge/EDT-2025.2+-blue)

Набор unit-тестов для проверки поведения [1С: Адаптер Kafka](https://github.com/ShadobaAI/kafka-adapter).

## Назначение

Репозиторий содержит модульные тесты и входит в локальный EDT workspace из четырёх проектов:

- `../base` — базовая конфигурация, собранная из `adapter/base` и `adapter/adapter`;
- `../examples` — расширение с тестовыми данными и примерами;
- `../unit` — это расширение с модульными тестами адаптера;
- `../yaxunit` — отдельный checkout ядра [YAxUnit](https://github.com/bia-technologies/yaxunit).

Скрипты `create_test_edt.py` и `create_test_edt.sh` пересобирают только `../base` из `adapter/base` и `adapter/adapter`. Расширения `examples`, `unit` и `yaxunit` остаются самостоятельными проектами EDT.

> Репозиторий предназначен только для разработки и проверки изменений адаптера. В промышленную эксплуатацию не поставляется.

## Инструменты

- [YAxUnit](https://bia-technologies.github.io/yaxunit/) — unit-тесты прикладной логики 1С.

## Теги тестов

В `ИсполняемыеСценарии()` теги задаются через `Тег()` после `ДобавитьТестовыйНабор()` или `Добавить*Тест()`. Все теги на русском языке:

- Каждый набор: общие теги категории `Модульные` или `Интеграционные` и имени проверяемого объекта, например `кфкПродюсеры`.
- Набор дополнительно: проверяемая операция, например `ПолучитьПараметры` или `УдалитьСообщения`; для групп интеграционного API — раздел, например `Администрирование` или `СхемыИПраваДоступа`.
- Тест: ожидаемое поведение, например `ВозвращаетЗначенияПоУмолчанию` или `УдаляетПоЗапросу`. В наборах с несколькими операциями тест дополнительно отмечен тегом операции, например `ПолучитьНастройкиБрокера`.

Теги набора учитываются при отборе всех вложенных тестов, включая параметризованные сценарии. Одинаковые операции и поведения в разных модулях используют одинаковые теги. Для методов с латиницей в имени теги русифицированы: `ПраваДоступа`, `ЗафиксироватьТранзакциюКафка`, `ОтменитьТранзакциюКафка`.

Примеры фильтров `run_yaxunit_tests`:

- `tags: ["Модульные"]` — все модульные проверки.
- `tags: ["УдалитьСообщения"]` — проверки удаления входящих и исходящих сообщений.
- `tags: ["ВозвращаетЗначенияПоУмолчанию"]` — проверки значений по умолчанию во всех трех регистрах параметров.
- `tags: ["УдаляетПоЗапросу"]` — сценарии удаления по запросу в разных модулях.
- `modules: ["РС_кфкВходящиеСообщения_ММ"], tags: ["УдаляетПоЗапросу"]` — один конкретный сценарий.

Несколько тегов объединяются по условию «ИЛИ»; фильтры тегов и модулей — по условию «И». Совместное указание общего и узкого тегов расширяет выборку: для точечного поиска используйте узкий тег и при необходимости фильтр модуля.

## Интеграционные тесты Kafka

Общий модуль `Обр_кфкИнтеграция_МО` проверяет обработку `кфкИнтеграция` через настоящую внешнюю компоненту и Kafka. Зарегистрирован 61 тестовый метод, 130 запусков с учетом параметризации. В сценариях и фикстурах присутствуют вызовы всех 102 экспортных методов API. Проверки функций включают тип и значение ответа; для JSON отдельно проверяются исходное представление и содержимое разобранного объекта. Это перечень реализованных проверок, а не утверждение об успешном прохождении: падение раннего утверждения может прервать последующие проверки сценария. См. [матрицу API](kfk-integration-coverage.md).

Стенд — `tools/kafka/docker-compose.yml` относительно корня Kafka workspace. Оба брокера должны быть доступны процессу 1С по `localhost:29091` и `localhost:29092`. Тесты ожидают идентификаторы брокеров `1` и `2`, создают топики с двумя партициями и фактором репликации `2`. При запуске 1С на другом компьютере или внутри контейнера адреса и ожидания стенда необходимо адаптировать.

Проверяются доступность и состав кластера, создание и удаление топиков, отказ повторного создания, доставка текста и пустого тела с ключом и заголовками, два способа пакетной отправки, чтение по смещению и через консьюмер, Base64, границы партиции, назначение и перемещение позиции, фиксация смещения, подтверждение и отмена транзакций. Отмена транзакции проверяется чтением следующей подтвержденной записи с `isolation.level=read_committed`.

Каждый сценарий с данными создает уникальный топик `yaxunit-integration-<UUID>` и использует отдельную группу `yaxunit-group-<UUID>`. Обработчик `ПослеКаждогоТеста` закрывает клиентов, отменяет незавершенную транзакцию и удаляет свой топик. У неактивной группы теста нет смещений других топиков: удаление единственного топика приводит к удалению последних смещений и группы. Очистка до 20 раз проверяет исчезновение группы через API списка групп; явно удалять ее повторно не требуется. Принудительное завершение процесса 1С может прервать очистку. Существующие пользовательские топики и группы тесты не изменяют; записи в справочниках и регистрах 1С не создаются.

Для запуска через `unit-edt` используйте конфигурацию `YAxUnit - Kafka Unit` и фильтр `modules: ["Обр_кфкИнтеграция_МО"]` в `run_yaxunit_tests`. Перед первым запуском проверьте состояние приложения через `get_applications`; требуемое обновление тестовой базы выполняется через `update_database` после явного разрешения на обновление. Не запускайте новые тесты против старой версии расширения в базе.

Дополнительно проверяются Schema Registry, создание/описание/удаление ACL, настройки топика и брокера, размер топика, удаление записей, группы консьюмеров, метрики, параметры компоненты, партишионеры, AVRO, Protobuf и устаревшие экспортные методы. Для изменения настроек брокера используется отрицательный сценарий с недопустимым размером сообщения; положительное изменение проверяется на собственном топике. Отсутствие брокера или внешней компоненты считается ошибкой окружения, а не успешным пропуском.

В тестовом расширении заимствована обработка `кфкИнтеграция` и добавлен метод `ют_СостояниеДляТестирования()`. Он позволяет проверить исходные значения всех четырех переменных объекта: подключенный `Коннектор`, два режима со значением `Ложь` и числовой `ТаймаутОжиданияОтвета = 500`. Проверяются изменения режимов и независимость экземпляров обработки. Исходная обработка адаптера не изменяется.

Проверки двоичных результатов сравнивают `ТипЗнч(Ответ)` с ожидаемым типом до сравнения Base64. Поэтому неверно возвращенная строка с управляющими символами не попадает в текст ошибки YAxUnit и не блокирует передачу отчета через XDTO.

Все тесты используют общий dev/test-кластер `node1/node2` на `localhost:29091,localhost:29092`. Поддержка ACL включена на обоих брокерах; Schema Registry на `http://localhost:38081` хранит схемы в этом же кластере. Конфигурация стенда находится в `tools/kafka/docker-compose.yml`. Применение из каталога этого репозитория:

```powershell
docker compose -f ../../../tools/kafka/docker-compose.yml up -d
```

Изменение настроек пересоздаст контейнеры брокеров с сохранением томов. ACL создаются только для уникального ресурса `yaxunit-acl-<UUID>`, схемы — для субъекта `yaxunit-schema-<UUID>`. Очистка удаляет только ресурсы сценария. `УдалитьГруппуКонсьюмеров()` вызывается только в отдельном тесте этого API. Общая очистка проверяет автоматическое исчезновение группы после удаления топика и не зависит от этого метода. Если группа не исчезла за отведенные попытки, тест завершается ошибкой очистки. Проверки ACL относятся к административному API: анонимный клиент стенда является суперпользователем.
