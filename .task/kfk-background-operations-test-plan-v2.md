# кфкФоновыеОперацииСлужебный: план и чек-лист тестирования v2

Дата: 11.09.2026. Статус: план реализации нового набора; выполнение не завершено.

Основа — контракты и риски из [плана v1](kfk-background-operations-test-plan.md). По уточнению пользователя, прежний набор примерно из 2500 тестов находится в спрятанном коммите с сообщением `kfk-background-operations-test-plan`. Это исторический пример избыточного объёма, а не исходный набор для миграции. Его поиск, восстановление, инвентаризация, матрица изменений и сравнение старых и новых прогонов не входят в задачу и не являются условием начала или приёмки реализации. Результат v2 оценивается по проверке контрактов на текущей ревизии, диагностике и фактическим прогонам нового набора. Указанные в v1 дефекты — сведения для проверки актуальных рисков, а прежние результаты не подтверждают новый набор.

## 1. Цель и изменение подхода

Защитить от потери сообщений, неверного подтверждения обработки, повреждения очередей и удаления нужных данных при приемлемой стоимости сопровождения. Единица планирования — наблюдаемый контракт и риск, а не каждый внутренний метод или комбинация параметров.

V2 заменяет требования v1 о самостоятельном тестировании каждого метода, применении всей матрицы ко всем методам группы и обязательных 100% строк. Реестр методов v1 остаётся навигационной картой. Независимые контракты, аварийные исходы и регрессии не исключаются ради уменьшения числа тестов.

- [ ] Для каждого критичного контракта указать успешный исход, опасный отказ, существенную границу и проверяемое состояние.
- [ ] Проверить все достижимые исходы решений, управляющих подтверждением, повтором, продвижением позиции и удалением данных. При составном решении показать независимое влияние условий и опасные взаимодействия.
- [ ] Для остальной логики использовать классы эквивалентности; дополнительные тесты добавлять по выявленному риску или пробелу.
- [ ] Измерять строки/ветви как средство поиска пробелов; непокрытый критичный путь блокирует приёмку независимо от общего процента.

## 2. Паттерны и их применение

Это адаптация подходов из других экосистем, а не предложение подключить Python/Java/C++ к запуску 1С.

| Паттерн | Применение в этом плане | Ограничение |
|---|---|---|
| Arrange–Act–Assert; один наблюдаемый результат | Подготовка очереди → одна операция → согласованный результат в очереди, назначении и позиции | Несколько утверждений одного контракта допустимы; несвязанные операции не объединять |
| Table-driven tests, как параметризация pytest | Именованные строки таблицы для одной семантики: статус задания, граница времени, ответ транспорта | Каждая строка считается отдельным запуском; таблица не превращается в декартово произведение |
| Sociable unit tests | Проверять алгоритм с настоящими внутренними помощниками; изолировать внешнюю границу | SQL, транзакции и межсеансовые эффекты требуют отдельных проверок на платформе |
| State-based testing вместо избыточных mocks | Проверять сохранённые сообщения, позицию, хэши и неизменность чужих данных | Кратность/порядок вызовов проверять, когда это контракт: запрет повторной отправки, закрытие ресурса |
| Test Data Builder | Небольшие смысловые конструкторы сообщения, очереди и указателя; значимые значения видны в тесте | Конструктор не запускает проверяемую операцию и не вычисляет за неё ожидаемый результат |
| Model-based/stateful testing | Короткая последовательность «назначить → завершить второй → перезапустить → завершить первый» с инвариантом позиции | Модель описывает множество незавершённых работ, не копирует алгоритм продукта |
| Property/metamorphic testing | Перестановка порядка завершения и изменение разбиения на порции сохраняют итоговый набор обработанных ключей | Только при одинаковых предусловиях и без изменения семантики дубликатов; фиксированный воспроизводимый корпус |
| Fault injection | Ошибка транспорта и ошибка сохранения на разных границах подтверждения | Не подменять внутренний алгоритм, состояние которого проверяется |
| Mutation testing как проверка силы теста | Для опасного решения назвать изменение, которое обязан обнаружить тест: `>` вместо `>=`, чужой ID позиции, раннее сохранение хэша | Мысленный разбор не равен выполненному mutation testing; изменение продукта этим планом не разрешено |

Источники: [pytest: параметризация](https://docs.pytest.org/en/stable/how-to/parametrize.html), [Martin Fowler: Unit Test](https://martinfowler.com/bliki/UnitTest.html), [GoogleTest: gMock Cookbook](https://google.github.io/googletest/gmock_cook_book.html), [Hypothesis: stateful tests](https://hypothesis.readthedocs.io/en/latest/stateful.html), [PIT: mutation testing](https://pitest.org/). Конкретные границы и приоритеты ниже — проектные решения v2.

## 3. Размер и организация набора

Три уровня проверок, выбираемые по контракту. Разделение на файлы само по себе не является сокращением.

| Уровень | Что проверяется | Зависимости |
|---|---|---|
| Быстрые модульные | Указатели, пакеты, решения, распределение, преобразование сообщений | Прямые вызовы, управляемые входы, подмена только внешних границ |
| Компонентные с ИБ | Реальные запросы, отборы, сохранение статусов, хэшей, очистка | Реальная тестовая ИБ, изоляция каждого теста; категория `Интеграционные` |
| Стендовые | Межсеансовая видимость, конкуренция, реальные ФЗ и транспортные соглашения | Отдельное окружение и явная очистка; категория `Интеграционные` |

Предварительный ориентир — 120–180 именованных запусков основного регрессионного набора, включая строки параметров и стендовые случаи. Это гипотеза планирования, не достигнутый результат и не запрет на необходимую проверку. При превышении 180 сначала пересмотреть повторения и фикстуры; сохранить обоснованные уникальные критичные случаи. Окончательный бюджет установить после пилота по позиции и отправке.

- [ ] Считать отдельно процедуры, параметризованные запуски, примеры генерации, длительность и объём фикстур.
- [ ] Для регистрации с более чем 8 вариантами провести краткую проверку: какую отдельную ошибку ловит каждая строка. Число 8 — сигнал ревью, не ограничение покрытия.
- [ ] Вынести повторяющуюся подготовку в небольшие помощники; не создавать универсальный сценарий с десятками переключателей.
- [ ] Группировать наборы по контрактам из раздела 5. Точные имена/размещение модулей выбрать по текущему владельцу и правилам YAxUnit перед реализацией.
- [ ] Использовать русские теги категории, объекта, операции и поведения согласно README; уровень изоляции и критичность добавить как теги отбора.
- [ ] Не создавать отдельные тесты для простой константы или делегирующего метода, если её ошибочное значение уже обнаруживается тестом контракта. Внешние UUID и таблицы соответствий проверить компактной таблицей там, где они самостоятельный контракт.

## 4. Правила отбора входов

1. Выбрать минимальный нормальный вход.
2. Для каждого условия найти вход, меняющий существенный результат. Неприменимые комбинации исключить с причиной.
3. Добавить границы реального решения: до/на/после порога. Не размножать одну границу по всем операциям при общей реализации.
4. Добавить известное опасное взаимодействие: пропущенная строка перед ошибкой транспорта, незавершённая порция перед завершённой, равные временные метки на границе пакета.
5. Сопоставить строки с контрактами. Повторы удалить только при сохранении утверждений и уровня проверки.

Пример A07 из v1: при подтверждённой независимости четырёх флагов достаточно базового состояния, четырёх одиночных включений и совместного включения как проверки объединения результата. Условия логирования/контроля проверяются отдельной компактной таблицей; их не перемножают автоматически с этими шестью входами. Если порядок, приоритет или взаимодействие флагов влияет на результат, соответствующие комбинации обязательны. Проверка независимости по актуальной реализации — подготовительный шаг, а не допущение о продукте.

Попарный отбор допустим для второстепенных настроек после анализа ограничений. Он не заменяет тесты отказов, временных последовательностей и сочетаний, управляющих потерей данных. Для малого критичного решения полный перебор четырёх булевых комбинаций может быть проще и надёжнее сокращения.

### Стендовые проверки

- [ ] BG-S01: два реальных ФЗ с контролируемым обратным завершением; проверить межсеансовую видимость назначений и позиции. Управлять порядком через согласованные сигналы, а не случайные паузы.
- [ ] BG-S02: аварийное завершение/отмена реального ФЗ и повторный запуск; проверить сохранение остатка, отсутствие лишнего задания и очистку тестового окружения.
- [ ] BG-S03: реальная транспортная граница Kafka для отправки/чтения и согласования offset с сохранением в ИБ. Ограничить поддерживаемыми гарантиями доставки, не заявлять exactly-once по результату модульных тестов.
- [ ] BG-S04: локальный HTTP-приёмник проверяет POST, gzip и ответ; Telegram изолирован на разрешённой границе. Недоступный контур — явный пробел, не успешный пропуск.

## 6. Фикстуры, изоляция и ожидаемые результаты

- [ ] Зафиксировать владельца `unit`, серверный контекст и актуальные точки входа через назначенные инструменты. Исходники `src/**` читать/менять только разрешёнными MCP; изменения — `unit-edt:8768`.
- [ ] До реализации сверить существующие фикстуры через `kfk-unit`; продуктовые зависимости — по разрешённым `kfk`/`kfk-base`. Этот документ не подтверждает текущий состав исходников.
- [ ] Создавать данные через подходящие публичные средства `ЮТест.Данные()`; значимые ключи, даты и статусы задавать явно и согласованно.
- [ ] Каждый тест владеет своими записями. Подготовка/очистка по умолчанию на уровне теста; общими могут быть неизменяемые описания, а не изменяемая очередь.
- [ ] Состояние ИБ проверять через `ЮТест.ОжидаетЧтоТаблицаБазы(...)` и специализированные утверждения ИБ. В результат включать контрольные чужие строки.
- [ ] Транзакционный откат выбирать только для кода, полностью выполняемого в этой транзакции. Реальные ФЗ, commit и внешние эффекты проверять вне обёртки с явной очисткой; автоматическое удаление созданных данных не восстанавливает произвольные изменения.
- [ ] Управлять временем/транспортом только через существующие допустимые границы. Если необходимой границы нет, зафиксировать препятствие; этот план не разрешает менять продукт или платформенные методы.
- [ ] Не копировать проверяемую формулу в ожидаемый результат. Для позиции использовать вручную разобранные последовательности; для пакетов — исходное мультимножество ключей; для внешнего сообщения — независимый эталон.
- [ ] Не мокировать расчёт указателя, SQL-отбор или сохранение хэша в тесте именно этого поведения. Подмену транспорта дополнить BG-S03.
- [ ] После ошибки восстанавливать mocks, контекст, настройки, записи и внешние ресурсы; проверять самостоятельный и повторный запуск.

## 7. Реализация нового набора

Набор строится по контрактам BG01–BG22 и BG-S01–BG-S04 на текущей реализации продукта. Отсутствие прежних тестов в рабочей ревизии не блокирует работу. Не воспроизводить избыточный перебор параметров, в том числе в скрытых циклах.

- [ ] Зафиксировать ревизию проверяемого продукта и нового набора.
- [ ] Для каждого контракта подобрать различающие входы, наблюдаемые утверждения и необходимый уровень проверки.
- [ ] Сначала реализовать BG03–BG05 и BG09–BG11; по фактическим прогонам оценить достаточность проверок, длительность и объём подготовки.
- [ ] Выполнить новые затронутые тесты в изолированных запусках; разобрать падения и проверить повторный запуск.
- [ ] Разобрать чувствительность критичных утверждений к ошибке границы, чужому ID, неверному индексу и раннему хэшу. Фактические мутационные эксперименты требуют отдельного разрешённого scope и инструментария.
- [ ] Устранить повторную проверку одного контракта и дублирование подготовки внутри нового набора, сохранив проверки разных опасных исходов.

Исторические наблюдения v1 относятся к рискам следующих контрактов: R01 → BG15; R02 → BG12; R03 → BG08; R04 → BG18; R05 → BG21; R06 → BG09; R07 → BG10; R08 и R10 → BG22; R09 → BG19. Проверять эти риски на текущей ревизии в рамках соответствующих контрактов. Пометка «исправлено» из v1 не заменяет актуальную проверку. Подтверждённый дефект получает отдельный воспроизводящий тест без размножения по всем операциям. Перенос старых тестов и отдельный отчёт об отличиях не требуются.

## 8. Порядок внедрения и приёмка

- [ ] Этап 1: проверка актуальных точек входа и доступных фикстур; реализация проверок позиции/пакетов/отправки, калибровка бюджета по новому набору.
- [ ] Этап 2: получение, дедупликация, очистка и сохранение — остальные P0; реальные проверки ИБ.
- [ ] Этап 3: P1 и стендовые контракты; устранение дублирующей подготовки и повторных проверок.
- [ ] На каждом изменении запускать затронутые тесты и быстрые критичные проверки. Перед слиянием — весь основной набор. Перед выпуском и после изменения межсеансовой/транспортной логики — соответствующий стендовый набор; полный стендовый прогон перед выпуском.
- [ ] При недоступном обязательном уровне писать «проверка не выполнена» и не объявлять полную приёмку. Падения не прятать автоматическими повторами или отключением регистрации.
- [ ] Для полной приёмки все применимые обязательные P0/P1 и стендовые проверки завершены успешно; исключения и отложенные риски не выдаются за выполненный план.
- [ ] Для BG01–BG22 и BG-S01–BG-S04 заполнены тест, вход, ожидаемое состояние, уровень, результат и ревизия. Все P0 закрыты содержательными утверждениями и обязательным уровнем проверки.
- [ ] В полном наборе проверены оба исхода критичных решений; пробелы по строкам/ветвям разобраны. Для некритичного непокрытого участка записаны причина и остаточный риск.
- [ ] Известные дефекты и ограничения текущей ревизии перечислены отдельно; неисправленный P0 препятствует полной приёмке.
- [ ] Для нового набора зафиксированы число запусков, примеры генерации, время подготовки/исполнения и наиболее дорогие фикстуры. Подготовка остаётся компактной, повторные проверки одного контракта устранены. Сравнение показателей со старым набором не требуется.
- [ ] Будущие изменения тестов проверены по загруженным паттернам YAxUnit, диагностике `unit-edt` до/после и целевому запуску. Для асинхронного запуска получен конечный результат того же задания; неожиданные 0 тестов считаются ошибкой.

Нормативная основа проектирования: корпус `v8std`, паттерны YAxUnit `authoring-baseline`, `test-module`, `naming`, `registration-and-parameters`, `assertions`, `test-data`, `data-isolation`, `mocking`, `dependencies`, `lifecycle-and-contexts`. При реализации дополнительно выбрать требования к реально изменяемым конструкциям BSL. План не содержит изменений 1С, не подтверждает покрытие и не разрешает изменения соседних репозиториев.
