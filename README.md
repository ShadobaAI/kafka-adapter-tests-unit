# 1С: Адаптер Kafka — Unit-Тесты

![Платформа](https://img.shields.io/badge/1С-8.3.21+-blue)
![EDT](https://img.shields.io/badge/EDT-2025.2+-blue)

Набор unit-тестов для проверки поведения [1С: Адаптер Kafka](https://github.com/ShadobaAI/kafka-adapter).

## Назначение

Репозиторий содержит модульные тесты и входит в локальный EDT workspace из четырёх проектов:

- `../base` — базовая конфигурация, собранная из `adapter/base` и `adapter/adapter`;
- `../examples` — расширение с тестовыми данными и примерами;
- `../unit` — это расширение с модульными тестами адаптера;
- `../yaxunit` — отдельный checkout ядра [YAxUnit](https://github.com/bia-technologies/yaxunit).

Скрипты `create_test_edt.py` и `create_test_edt.sh` пересобирают только `../base` из `adapter/base` и `adapter/adapter`. Расширения `examples`, `unit` и `yaxunit` остаются самостоятельными проектами EDT.

> Репозиторий предназначен только для разработки и проверки изменений адаптера. В промышленную эксплуатацию не поставляется.

## Инструменты

- [YAxUnit](https://bia-technologies.github.io/yaxunit/) — unit-тесты прикладной логики 1С.

## Теги тестов

В `ИсполняемыеСценарии()` теги задаются через `Тег()` после `ДобавитьТестовыйНабор()` или `Добавить*Тест()`. Все теги на русском языке:

- Каждый набор: общие теги категории `Модульные` или `Интеграционные` и имени проверяемого объекта, например `кфкПродюсеры`.
- Набор дополнительно: проверяемая операция, например `ПолучитьПараметры` или `УдалитьСообщения`; для групп интеграционного API — раздел, например `Администрирование` или `СхемыИПраваДоступа`.
- Тест: ожидаемое поведение, например `ВозвращаетЗначенияПоУмолчанию` или `УдаляетПоЗапросу`. В наборах с несколькими операциями тест дополнительно отмечен тегом операции, например `ПолучитьНастройкиБрокера`.

Теги набора учитываются при отборе всех вложенных тестов, включая параметризованные сценарии. Одинаковые операции и поведения в разных модулях используют одинаковые теги. Для методов с латиницей в имени теги русифицированы: `ПраваДоступа`, `ЗафиксироватьТранзакциюКафка`, `ОтменитьТранзакциюКафка`.

Примеры фильтров `run_yaxunit_tests`:

- `tags: ["Модульные"]` — все модульные проверки.
- `tags: ["УдалитьСообщения"]` — проверки удаления входящих и исходящих сообщений.
- `tags: ["ВозвращаетЗначенияПоУмолчанию"]` — проверки значений по умолчанию во всех трех регистрах параметров.
- `tags: ["УдаляетПоЗапросу"]` — сценарии удаления по запросу в разных модулях.
- `modules: ["РС_кфкВходящиеСообщения_ММ"], tags: ["УдаляетПоЗапросу"]` — один конкретный сценарий.

Несколько тегов объединяются по условию «ИЛИ»; фильтры тегов и модулей — по условию «И». Совместное указание общего и узкого тегов расширяет выборку: для точечного поиска используйте узкий тег и при необходимости фильтр модуля.

## Тесты обработки кфкИнтеграция

Серверный общий модуль `Обр_кфкИнтеграция_МО` объединяет два вида проверок:

- `Интеграционные` — работа через настоящую внешнюю компоненту с Kafka и Schema Registry.
- `Модульные` — проверка BSL-логики обработки с подменой внешней Kafka-компоненты: передача аргументов, преобразование JSON, пустые ответы, ошибки и граничные значения.

Сценарии охватывают администрирование кластера, топики и группы консьюмеров, отправку и чтение сообщений, транзакции, метрики, настройки, ACL, AVRO и Protobuf. Для ответов проверяются тип и содержимое, для операций — наблюдаемое состояние. Серверные тесты не исполняют клиентскую препроцессорную ветвь обработки.

Соответствие сценариев API, результаты запусков и методика измерения покрытия хранятся отдельно в [чеклисте покрытия](kfk-integration-coverage-checklist.md).

### Стенд и запуск

Интеграционные тесты используют общий dev/test-кластер `node1/node2`. Брокеры должны быть доступны процессу 1С по `localhost:29091` и `localhost:29092`, Schema Registry — по `http://localhost:38081`. Тесты ожидают идентификаторы брокеров `1` и `2`, создают топики с двумя партициями и фактором репликации `2`. При запуске 1С на другом компьютере или в контейнере адреса и ожидания стенда необходимо адаптировать.

Конфигурация стенда — `tools/kafka/docker-compose.yml` относительно корня Kafka workspace. Запуск из каталога этого репозитория:

```powershell
docker compose -f ../../../tools/kafka/docker-compose.yml up -d
```

На обоих брокерах включена поддержка ACL. Проверки ACL относятся к административному API: анонимный клиент стенда является суперпользователем. Отсутствие брокера или внешней компоненты при интеграционном запуске считается ошибкой окружения.

Для запуска через `unit-edt` (порт `8768`) используется конфигурация `base Тонкий клиент`. Перед первым запуском проверьте состояние приложения через `get_applications`. При наличии разрешения на обновление тестовой базы передайте в `run_yaxunit_tests`:

```json
{
  "launchConfigurationName": "base Тонкий клиент",
  "modules": ["Обр_кфкИнтеграция_МО"],
  "updateBeforeLaunch": true,
  "updateScope": "extension:unit",
  "externalInfobaseChanges": "cancel",
  "timeout": 45
}
```

Для выбора вида проверок добавьте `tags: ["Модульные"]` или `tags: ["Интеграционные"]`. Если инструмент вернул Pending, продолжайте через `get_job_status` с полученным `jobId`, не создавая повторный запуск.

### Изоляция данных

Сценарии создают собственные ресурсы с UUID в имени: топики `yaxunit-integration-<UUID>`, группы `yaxunit-group-<UUID>`, ресурсы ACL `yaxunit-acl-<UUID>` и субъекты схем `yaxunit-schema-<UUID>`.

Обработчик `ПослеКаждогоТеста` закрывает клиентов, отменяет незавершенную транзакцию и удаляет ресурсы сценария. После удаления топика очистка ожидает автоматического исчезновения неактивной группы до 10 секунд с проверками каждые 250 мс; превышение срока считается ошибкой очистки. `УдалитьГруппуКонсьюмеров()` вызывается отдельно в тесте этого API.

Пользовательские топики и группы не изменяются; записи в справочниках и регистрах 1С не создаются. Принудительное завершение процесса 1С может прервать очистку.

### Тестовая инфраструктура

`ют_КоннекторИнтеграцииДляТестов` хранит заданные ответы и журнал вызовов в контексте текущего теста. Перехват фабрики в заимствованном `ОбщегоНазначения` подменяет только Kafka-компоненту при наличии такой настройки; исполняется исходная BSL-логика обработки.

Заимствованная обработка `кфкИнтеграция` предоставляет методы `ют_СостояниеДляТестирования()` для проверки состояния экземпляра и `ют_ПодключитьКомпонентуДляТестирования()` для проверки отказа подключения на созданном объекте. Эти методы принадлежат тестовому расширению `unit`.

При добавлении наборов используйте уникальные имена в пределах тестового модуля, в том числе для модульных и интеграционных проверок одного API. В проверках двоичных ответов сначала сравнивайте тип, затем содержимое: это предотвращает попадание управляющих символов в текст ошибки и отчет XDTO.
